# AI 2040 Verification — Prototype Implementation

**Status: work in progress — 21 of 30 sections drafted.** This is not a finished project; it's a section-by-section engineering exploration, shared at its current state rather than held back until (or if) all 30 sections are done. See the progress table near the top of [`ai-2040-verification.md`](./ai-2040-verification.md) for exactly which sections are drafted and which are still pending — that table is the authoritative status, not this README.

## What this is

An attempt to actually *build* pieces of the compute-governance verification architecture described in the AI Futures Project's [*AI 2040: Plan A*](https://ai-2040.com) (specifically its [Verification Plan supplement](https://ai-2040.com/supplements/verification-plan), July 2026) and the real [DiFR](https://arxiv.org/abs/2511.20621) inference-verification scheme — not a slide deck describing what such a system would do, but working code: a real trained language model, a real FastAPI + PostgreSQL verification server, a real Rust packet-capture/hashing pipeline, real red-team attacks run against the real server, and so on.

The guiding rule throughout is **honesty over inflation**: this sandbox has no GPU, one logical CPU, no DPDK-capable NIC, and no reachable path to real pretrained weights. Rather than paper over that, every section says plainly what was actually measured here vs. what's a design estimate, cites real external sources for anything not independently testable in this environment, and reports bugs the testing process actually caught (a few real ones are documented in `ai-2040-verification.md` — a CRLF-fragmentation bug in the stream reassembler, a hard-label-vs-soft-KD gradient bug in a distillation run, a fabricated RSA implementation found in an externally-sourced document and rejected rather than reused, among others).

## Layout

```
ai-2040-verification.md   the actual document — technical write-up for every drafted
                           section, each with a self-check and source list
*.py                       the Python side: the DiFR verification server, the trained
                           character-LM, LoRA backdoor adapters, the red-team suite,
                           calibration sweeps, the tamper-evident log, etc.
*.json                     real output from actual runs of the scripts above (test
                           suite results, calibration AUC sweeps, disk benchmarks, ...)
wipe_daemon.c               the memory-wipe daemon (§15), AES-NI DAG labeling + full
                           overwrite; verifier.py independently re-checks its output
tap_reader/                 a Rust crate: passive-tap packet parsing, hashing, HTTP
                           chunked/SSE stream reassembly, a lock-free evidence ring
                           buffer, the sampling gateway, and Merkle/epoch commitments
                           (§2-§4). Has its own README with build/benchmark commands.
```

## Reproducing this

**Rust (`tap_reader/`)** is fully self-contained and was confirmed to build clean from this exact layout: `cd tap_reader && cargo build --release && cargo test --release` (17/17 unit tests pass). See `tap_reader/README.md` for the individual benchmark binaries.

**Python** needs `pip install -r requirements.txt`. A few scripts depend on data artifacts that are generated by *other* scripts rather than checked in here (consistent with not committing large binary blobs): `train.py` needs `shakespeare.txt` (the tiny-shakespeare corpus, cited in §5 as pulled from `raw.githubusercontent.com/karpathy/char-rnn`) and produces `charlm.pkl` + `vocab.pkl`; `train_variants.py` (needs `charlm.pkl` first) produces the same-family/cross-family checkpoints; `lora.py` (needs `charlm.pkl` + `vocab.pkl`) produces the backdoor adapters. Run those three, in that order, before anything that loads a `.pkl` checkpoint (`server.py`, `test_suite.py`, `redteam.py`, `calibration.py`, etc.). `db.py` expects a local PostgreSQL instance (`difr_verification` database, matching the DSN at the top of `db.py`).

## What this isn't

Not a claim that any of this is production-ready, that the small NumPy character-LM stands in for a frontier model's capability, or that sandbox-measured throughput numbers (single CPU core, no NIC) predict real datacenter numbers. `ai-2040-verification.md` is explicit about this at every point it matters — read a section's own "Self-check" and "Sources used" before taking a number out of context.
